# Dashboard Builder

A drag-and-drop dashboard builder, similar to the building blocks in Canva or Figma. You add **sections** to a canvas and fill them with **rich text**, **images** and **bar/line charts**. Sections and elements can be dragged and resized, and the whole layout (position, size and content) is saved in **MySQL** and rendered again on reload.

**Stack:** **backend/**: Node.js · Express 5 (layered MVC) · MySQL 8. **frontend/**: Vite · vanilla JavaScript ES modules · Chart.js.

> The brief specifies a LAMP backend (PHP + MySQL). As requested, the backend here is **Node.js + MySQL** and provides the same save/retrieve layout APIs.

---

## Features

| Requirement | Implementation |
|---|---|
| Add, move and resize **sections** | Click **Section** in the palette, or drag it onto the canvas. Move it by its body or title label and resize it with 8 handles. |
| **Text editor**: bold, italic, font size | Double-click a text element. The toolbar has bold, italic, underline, font size (10–64 px), color, lists, alignment and clear formatting. |
| **Image upload and placement** | Upload PNG, JPEG, GIF or WEBP (max 5 MB, checked by magic bytes). Set fit (cover/contain/stretch) and alt text. Drag and resize like any element. |
| **Graphs** (bar/line), at least one generated dynamically | Chart.js charts. *Manual* data is edited in a spreadsheet-like table. *Dynamic* data is generated by the API (`/api/chart-data/:dataset`), with optional auto-refresh every 5–60 s. |
| Every element **draggable and resizable** | Pointer-event based, so it works with mouse, touch and pen. Optional snap to a 10 px grid. Elements stay inside their section, and sections stay inside the canvas. |
| **Save the layout** to MySQL | `PUT /api/dashboards/:id/layout` saves every section and element in a single transaction. |
| **Fetch and render on reload** | `GET /api/dashboards/:id` returns the full layout, and the builder renders it. |
| HTML5 Canvas / Chart.js | Chart.js renders to `<canvas>`. It is bundled by Vite, so no CDN is needed. |
| **Responsive** | Desktop first. Below 1100 px the panels shrink. Below 860 px the side panels become slide-in drawers and the canvas scales to fit. In preview mode on narrow screens, sections stack vertically and scale to the screen width. |

**Additional features:** login with per-user dashboards, undo/redo (Ctrl+Z / Ctrl+Y), keyboard shortcuts (Delete, Ctrl+D duplicate, arrow-key nudge, Ctrl+S save), bring to front / send to back, a preview mode, a properties inspector with live validation, an unsaved-changes indicator with a warning before leaving the page, and detection of edits made in another tab (409 conflict handling).

## Quick start

### Prerequisites
- **Node.js 18.18+** (tested on Node 24) and npm 9+
- **MySQL 8.0+** (local install, or Docker)

### 1. Install dependencies (both workspaces, from the root)
```bash
npm install
```

### 2. Start MySQL
Use an existing MySQL 8 server, or start one with Docker:
```bash
docker compose up -d mysql          # root password: rootpass, port 3306
```

### 3. Configure the backend environment
```bash
cp backend/.env.example backend/.env      # Windows: copy backend\.env.example backend\.env
```
Edit `backend/.env` if your MySQL credentials differ, and set a random `JWT_SECRET`:
```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

| Variable | Default | Description |
|---|---|---|
| `PORT` | `5000` | API port |
| `CLIENT_ORIGINS` | `http://localhost:5173` | Comma-separated browser origins allowed to call the API (the Vite dev server) |
| `FRONTEND_DIST` | `../frontend/dist` | Built frontend served by the API in production (relative to `backend/`) |
| `DB_HOST` / `DB_PORT` | `127.0.0.1` / `3306` | MySQL server |
| `DB_USER` / `DB_PASSWORD` | `root` / `rootpass` | MySQL credentials (need CREATE privileges for setup) |
| `DB_NAME` | `dashboard_builder` | Database name |
| `JWT_SECRET` | *(required, ≥ 32 chars)* | Signs session tokens |
| `JWT_EXPIRES_IN` | `7d` | Session lifetime |
| `COOKIE_SECURE` | `false` | Set `true` behind HTTPS |
| `UPLOAD_MAX_MB` | `5` | Max image size |

All variables are validated at startup. If any are invalid, the API prints a clear message and exits. The frontend needs no `.env`. Optionally set `VITE_API_TARGET` if the API isn't on `http://localhost:5000`.

### 4. Create the database (schema and sample data)
```bash
npm run db:setup      # idempotent: creates the DB, tables and sample data
npm run db:reset      # drops and recreates everything (destroys data)
```

### 5. Run

**Development** (two processes, with hot reload):
```bash
npm run dev
```
| Process | URL | Notes |
|---|---|---|
| Frontend (Vite) | **http://localhost:5173** | Open this one. It proxies `/api` and `/uploads` to the API. |
| Backend (Express) | http://localhost:5000 | REST API (`node --watch`) |

**Production** (one process: the API also serves the built frontend):
```bash
npm run build         # builds frontend/dist
npm start             # http://localhost:5000
```

Sign in with the demo account:

> **Email:** `demo@example.com` **Password:** `Demo@1234`

The demo account includes a sample *Sales Overview* dashboard with text, an image, a manual bar chart and a live dynamic line chart. It also has an empty dashboard to build on.

### Alternative: everything in Docker
```bash
docker compose up --build           # MySQL + app on http://localhost:5000
```

### Tests
```bash
npm test              # backend (40) + frontend (10)
```
- **Backend:** API integration and unit tests (Node's built-in test runner plus supertest). They run against a separate `<DB_NAME>_test` database that is recreated automatically, so MySQL must be running. They cover auth, validation, ownership isolation, layout save and reload, XSS sanitization, geometry rules, version conflicts, upload security and chart data.
- **Frontend:** unit tests for validators, redirect safety, routing and builder geometry.

### Root scripts

| Script | What it does |
|---|---|
| `npm run dev` | API + Vite dev server together (`concurrently`) |
| `npm run build` | Production build of the frontend |
| `npm start` | API server (serves `frontend/dist` when it exists) |
| `npm run db:setup` / `db:reset` | Create or recreate the database |
| `npm test` | Backend and frontend test suites |

Each workspace can also be run on its own, e.g. `npm run dev -w backend` or `npm run dev -w frontend`.

## Using the builder

1. **Add a section:** click **Section** in the left palette, or drag it onto the canvas.
2. **Add elements:** click **Text**, **Image**, **Bar chart** or **Line chart**. The element goes into the selected section (or a new one), at the first free spot. You can also drag a palette item onto a specific section.
3. **Arrange:** drag elements to move them and use the handles to resize. Live position and size badges are shown while you drag. The inspector on the right accepts exact X, Y, width and height values.
4. **Edit text:** double-click a text element (or press Enter). Use the toolbar at the top, and press Esc to finish.
5. **Images:** double-click an image, or use **Upload image** in the inspector.
6. **Charts:** choose bar or line, a title, and the data source:
   - *Manual:* edit labels and values in the table, and add or remove rows and series.
   - *Dynamic:* pick a dataset (sales, traffic, sign-ups, CPU) and the number of points. Turn on auto-refresh for a live chart.
7. **Save:** use the **Save** button or Ctrl+S, then reload to confirm the layout persists. **Preview** hides the editor chrome.

**How the two halves connect:**
- **Development:** the browser talks only to Vite (`:5173`), which proxies `/api` and `/uploads` to Express (`:5000`). From the browser's point of view everything is same-origin, so the httpOnly session cookie just works.
- **Production:** `npm run build` writes `frontend/dist`, and Express serves those pages on clean URLs (`/login`, `/dashboards`, `/dashboards/:id`) next to the API on one origin. Protected pages are guarded on the server (redirect to `/login`) and again on the client (`guards/authGuard.js`).
- **Validation:** the frontend loads the API's limits from `GET /api/meta/config`, so client-side checks always match the server's rules.

**Adding a new element type:** implement `{ label, defaults(), mount() }` in `frontend/src/features/builder/elements/<type>/`, register it in `elements/registry.js`, add its inspector fields, then add a Joi content schema in `backend/src/validators/dashboard.validator.js`.

## REST API

All responses are JSON. Success responses look like `{ "data": ... }` and errors look like `{ "error": { "code", "message", "details?": [{ "field", "message" }] } }`.

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/auth/register` | `{ name, email, password }` → creates a user and starts a session |
| POST | `/api/auth/login` | `{ email, password }` → starts a session (httpOnly cookie) |
| POST | `/api/auth/logout` | Ends the session |
| GET | `/api/auth/me` | The current user |
| GET | `/api/dashboards` | Lists the user's dashboards, with section and element counts |
| POST | `/api/dashboards` | `{ name, description?, canvasWidth?, backgroundColor? }` |
| GET | `/api/dashboards/:id` | **Retrieves the layout**: the dashboard plus its sections and their elements |
| PATCH | `/api/dashboards/:id` | Updates name, description, canvas width or background |
| PUT | `/api/dashboards/:id/layout` | **Saves the layout**: `{ version, settings?, sections: [{ ..., elements: [...] }] }` |
| PUT | `/api/dashboards/order` | `{ ids: [3, 1, 2] }` → saves the drag-and-drop order of "My dashboards" |
| DELETE | `/api/dashboards/:id` | Deletes the dashboard and its layout (cascade) |
| POST | `/api/uploads/images` | multipart field `image` → `{ url }` |
| GET | `/api/chart-data` | Lists the dynamic datasets |
| GET | `/api/chart-data/:dataset?points=N` | Freshly generated chart data |
| GET | `/api/health` | Liveness check, including the DB |
| GET | `/api/meta/config` | Validation limits and chart datasets shared with the frontend |

<details>
<summary>Example layout payload</summary>

```json
{
  "version": 3,
  "settings": { "name": "Sales", "description": "", "canvasWidth": 1200, "backgroundColor": "#f4f6fb" },
  "sections": [{
    "title": "Revenue", "x": 20, "y": 30, "width": 600, "height": 380, "zIndex": 1, "backgroundColor": "#ffffff",
    "elements": [
      { "type": "text", "x": 20, "y": 20, "width": 300, "height": 80, "zIndex": 1,
        "content": { "html": "<p><b>Hello</b></p>", "backgroundColor": "transparent" } },
      { "type": "chart", "x": 20, "y": 110, "width": 540, "height": 250, "zIndex": 2,
        "content": { "chartType": "bar", "title": "Q", "source": "manual", "dataset": "sales", "points": 3,
                     "refreshSeconds": 0, "labels": ["Q1", "Q2", "Q3"],

    ]
  }]
}
```
</details>

**Layout rules enforced by the API (422 if violated):** elements must stay within their section, and sections within the canvas width. Manual chart series must have one value per label. Images must have been uploaded by the same user. The limits are 50 sections, 30 elements per section and 300 elements per dashboard. A save with an out-of-date `version` returns **409 `VERSION_CONFLICT`**; the builder then offers to overwrite.

## Database schema

```
users (id, name, email UNIQUE, password_hash, timestamps)
  └─< dashboards (id, user_id FK, name, description, canvas_width, background_color, version, timestamps)
        └─< sections (id, dashboard_id FK, title, pos_x, pos_y, width, height, z_index, background_color)
              └─< elements (id, section_id FK, type ENUM(text,image,chart), pos_x, pos_y, width, height, z_index, content JSON)
users └─< uploads (id, user_id FK, stored_name UNIQUE, original_name, mime_type, size_bytes)
```
All foreign keys use `ON DELETE CASCADE`. Element positions are relative to their section. `content` holds the type-specific configuration: sanitized HTML, an image reference, or the chart config. See `database/schema.sql`.

## Security

- **Authentication:** passwords are hashed with bcrypt (12 rounds) and must meet a strength policy. The JWT lives in an `httpOnly`, `SameSite=Strict` cookie (and `Secure` when HTTPS is enabled). Login takes the same time whether or not the email exists, so it can't be used to discover accounts. Auth endpoints are rate-limited.
- **Authorization:** every query is scoped by `user_id`. Another user's dashboard returns 404 rather than 403, so IDs can't be enumerated. Uploaded images are only served to their owner.
- **Input validation:** Joi schemas validate every body, parameter and query, and unknown fields are stripped. The builder repeats the same rules in the browser for instant feedback (limits are shared from the server).
- **XSS:** rich text is sanitized against a whitelist on the server (`sanitize-html`) and in the browser (DOMParser-based). Pasting inserts plain text only. All other user data is rendered with `textContent` (never `innerHTML`). A strict Content Security Policy is set in production (`script-src 'self'`, no inline scripts).
- **Uploads:** the file type is detected from magic bytes, not the extension or MIME type, so SVG/HTML can't slip through. Files get random UUID names, there is a size limit, and they are served with `X-Content-Type-Options: nosniff`.
- **SQL injection:** only parameterized queries are used (`mysql2` placeholders).
- **CSRF:** SameSite=Strict cookies plus a same-origin check on all state-changing API requests.
- **Other:** Helmet security headers, a 1 MB JSON body limit, a guard against open redirects after login, and generic 500 responses that never include internal details.

## Troubleshooting

| Problem | Fix |
|---|---|
| `Could not connect to MySQL (ECONNREFUSED)` | Start MySQL (`docker compose up -d mysql`) and check `DB_HOST`/`DB_PORT`. |
| `ER_ACCESS_DENIED_ERROR` | Check `DB_USER`/`DB_PASSWORD` in `backend/.env`. |
| `ER_BAD_DB_ERROR` | Run `npm run db:setup`. |
| `Invalid environment configuration` | Copy `backend/.env.example` to `backend/.env` and set a `JWT_SECRET` of at least 32 characters. |
| Port 3306 already in use | Stop the other MySQL, or change the port mapping in `docker-compose.yml` and `DB_PORT`. |
| `localhost:5173` shows "Cannot reach the server" | The API isn't running. Use `npm run dev` (starts both), or start it with `npm run dev -w backend`. |
| `403 Cross-origin request blocked` | Add the frontend's origin to `CLIENT_ORIGINS` in `backend/.env`. |
| `npm start` serves only the API (no pages) | Run `npm run build` first, so `frontend/dist` exists. |
